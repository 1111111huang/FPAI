| BUG-011 | SnapshotStore mode/match_id never reached tool-execution thread — record and replay silently behaved as live | `SnapshotStore` (A09) stores `mode`/`match_id`/`match_date` in `threading.local()`. LangGraph's `ToolNode` executes every tool call — even a single one — via `langchain_core.runnables.config.get_executor_for_config()`, which returns a `ContextThreadPoolExecutor`. That executor runs the tool call on a *different* OS thread than the one that called `configure_snapshot_store()`. `ContextThreadPoolExecutor` explicitly copies `contextvars.Context` into its worker (`copy_context().run(...)`), but never touches `threading.local()`, which is strictly per-OS-thread. So the worker thread's `SnapshotStore._local` was always a fresh, uninitialized `threading.local()`, and `mode` silently defaulted to `"live"` regardless of what the calling thread had configured. Effect: `agent-snapshot` ("record" mode) called the real `ForecastService`/Tavily every time but never wrote a snapshot file — every match still got a `_complete.json` marker and printed "OK" because the live call succeeded; `agent-backtest` ("replay" mode) never read a recorded file either, so it silently made fresh live calls and never once raised `SnapshotMissingError`, even though the snapshot corpus on disk was entirely empty (24 directories containing only `_complete.json`, zero tool-response files). This also disabled the `before:<date>` web_search leakage filter (gated on `mode in ("record", "replay")`), since mode always read as `"live"`. Caught because the user manually inspected `data/agent_snapshots/` and found zero tool-call files despite 24/24 "successful" runs — no automated test caught it because all existing `SnapshotStore`/tool tests call `configure_snapshot_store()` and the tool function on the *same* thread, never exercising the real `ToolNode` dispatch path. | fixed | Switched `SnapshotStore` from `threading.local()` to `contextvars.ContextVar` (`src/agent/snapshot_store.py`) — `ContextThreadPoolExecutor` and `asyncio.to_thread` (used by `agent-backtest --concurrency`) both explicitly propagate `contextvars.Context` into worker threads, while a bare `threading.Thread()` (not used anywhere in this codebase) still correctly does *not* inherit it, preserving the cross-match isolation A09/A14 need. Proven via: an isolated repro showing `threading.local()` fails and `contextvars.ContextVar` succeeds across a real `ContextThreadPoolExecutor`; a new regression test `test_mode_and_match_propagate_into_context_thread_pool_executor`; a live single-match `agent-snapshot` run showing real `forecast_league_*.json`/`web_search_*.json` files now appear with `before:2026-03-16` correctly appended to the search query; and a canary-injection test that doctored a recorded `forecast_league` response and confirmed `agent-backtest` replay returned the doctored content rather than a fresh live forecast. Entire A20/A21 pilot corpus and both backtest reports were discarded and re-collected/re-run after the fix — see `agent_techspec.md` Section 18 for the corrected baseline. |
| BUG-013 | Agent can emit `recommendation_type: "direct_bet"` with `current_odds: null` | The LLM's own reasoning occasionally marks a market as a `direct_bet` while `current_odds` is `null` — logically incoherent, since "direct bet now" implies acting on a specific price that in this case doesn't exist (typically because odds were found for other markets in the same match but not this one). First observed during the A21 backtest baseline (`agent_techspec.md` §18.3): this crashed `simulate_flat_stake`/`simulate_kelly_stake` with `TypeError: float() argument must be ... not 'NoneType'`, because `staking.py`'s skip-gate checked `recommendation_type == "direct_bet"` and `correct is not None` but never guarded `current_odds` itself. Only the downstream symptom was patched (both staking functions now also skip when `current_odds is None`, with 2 regression tests in `tests/test_staking.py`) — the root cause, the agent producing this invalid combination in the first place, was never addressed at the prompt/reasoning level. Now directly relevant again: the web app (`documents/app_user_stories.md`) is a second, independent consumer of the same `MatchRecommendation` output (W02's API layer, W16's UI rendering), and will hit the identical invalid combination without its own defensive handling. | open | Backtest-staking symptom fixed (2026-06-27, part of A21). Root cause (agent-side) tracked as `agent_user_stories.md` A28 (Phase 10, Output Validation Hardening), which downgrades a `direct_bet` with no odds to `no_bet`/`insufficient_data` at extraction time. App-side defensive handling tracked separately as `app_user_stories.md` W02/W16. |

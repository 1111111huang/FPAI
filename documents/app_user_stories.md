# FPAI Web App — Design Discussions & User Stories

This document tracks the third FPAI component: a bettor-facing web app (`app/`) built on top of the ML forecasting engine (`FPAI_PRD.md`) and the LangGraph betting agent (`agent_prd.md`). Stories are prefixed `W##` to distinguish them from the ML forecasting engine (`US#`) and agent (`A##`) stories.

**Status:** functionality is still being worked out. Unlike the other two story documents, this one leads with an open discussion log. Nothing in the Open Design Discussions section is a decision — items only graduate into the Stories table once we've actually agreed on them. `documents/app_prd.md` and `documents/app_techspec.md` are drafts and will be filled in as these discussions resolve.

---

## Confirmed So Far

These came out of initial brainstorming and are treated as settled unless something below reopens them:

- **Primary user:** an individual bettor (not an internal analyst dashboard) — same user described in `agent_prd.md` Section 2.1.
- **Tech stack:** Next.js/React + TypeScript frontend, FastAPI backend wrapping the existing Python agent/forecast code.
- **Auth:** single-user, no accounts, for the MVP.
- **Bet tracker:** logs bets the user actually placed (not automatic hypothetical tracking).
- **"Why" explanation:** expandable static detail from the already-generated payload — no new on-demand LLM call.
- **Directory:** new top-level `app/` (vs. `frontend/`, `webapp/`, `dashboard/`).
- **Fixture discovery (D1):** fixtures are fetched from an external fixtures/results API (which provider is still open — see D1a below), and each fetched match is sent to the agent to generate a recommendation. No manual home/away/date entry as the primary flow.
- **Recommendation generation (D2):** the agent generates a recommendation (including its existing natural-language explanation) for every match displayed in the app. No follow-up/interactive Q&A from the user — one generation per match, that's it.
- **"Why" panel scope (D4):** pure text. No charts, no structured widgets, no interactivity — just the explanation (and other text fields like confidence/limitations) rendered as text.
- **Bet tracker lifecycle (D3, partial):** user selects a match in the app and records the bet they placed against it (market/selection/stake/odds); the app later fetches the actual match result and auto-records the outcome (via the same fixtures/results API as D1). Exact field list and status values still to be nailed down — see D3a.
- **Backend/engine boundary (D5):** fixture discovery, recommendation orchestration/caching, and bet tracking logic all live in `app/backend` as app-specific glue. `src/agent` and `src/forecast` are unchanged, called as libraries.
- **Local dev practice (D7):** standard two-process local dev — Next.js dev server (`npm run dev`) and FastAPI via `uvicorn --reload`, talking over HTTP with CORS (or a Next.js rewrite proxy) rather than a shared process. No Docker for the prototype phase; revisit containerization only if this moves beyond local dev.
- **Fixtures/results provider (D1a):** `football-data.org`. Used both to discover upcoming fixtures (D1) and to fetch actual results for bet auto-settlement (D3). Free-tier rate limits will need to be respected by the caching/orchestration layer (see D2a).
- **Visual design (D6):** dark mode only (locked, not auto/light), Tailwind CSS with hand-rolled components (no design-system library like shadcn/Radix), high visual density with card-based match displays, real club-color identity badges (config-driven — see `TEAM_COLORS` in the sandbox), system-ui sans, Phosphor icons, plain CSS transitions (150ms) for hover/expand — no animation library. Validated in the `sandbox/` prototype across all three pages (Dashboard, Match Explorer, Match Analysis) before being ported into the real `app/frontend`.
- **Recommendation generation timing (D2a):** not on-demand/on-page-load. Two scheduled triggers instead: (1) an end-of-day batch, once daily at end-of-day America/New_York time (handles EST/EDT correctly via `zoneinfo`, not a fixed UTC offset — exact trigger time TBD, proposed 23:00), which discovers the next day's fixtures and generates+caches an initial recommendation for each; (2) a per-match refresh 30 minutes before kickoff, re-running the agent with freshly-fetched odds since odds tend to settle close to kickoff. The dashboard/API always reads from the cache in the normal path — it does not call `run_agent()` synchronously on a user request. A manual "regenerate now" escape hatch remains for dev/testing and late-added fixtures.
- **Odds data source (D2b):** The Odds API, free tier (~500 credits/month), scoped tightly — 1X2 market only, single region — for E0 fixtures only (our only real-data-coverage league today anyway). football-data.org (D1a) turned out to have **no odds on its free tier at all** (verified: odds are a paid add-on, €15/month, requiring a paid base plan too — €27+/month minimum) — it remains the fixtures/results provider, but odds now come from a second, separate provider. The scheduled odds refresh (D2a) must degrade gracefully (skip, keep last-known odds) if the monthly credit budget is exhausted rather than erroring.
- **Bet tracker field list & logging paths (D3a):** every logged bet records date, home/away team, the bet (market + selection), odds, outcome (`open` → `won`/`lost`; void/push deferred), stake, and profit/loss (`stake × (odds − 1)` if won, `−stake` if lost, `null` while open). Two ways to log a bet: (1) **from a recommendation** — user picks a recommendation card and every field is auto-filled and locked except stake, which is the only input; the full recommendation JSON is snapshotted at log time (recommendations aren't reproducible run-to-run — agent_techspec.md §18.6); (2) **manual entry** — user selects a real fixture via the Match Explorer's existing search (not freeform team-name typing, so auto-settlement still works) and fills in market/selection/odds/stake themselves; no recommendation snapshot for this path.
- **Agent invocation ownership (2026-07-11):** the app is always the party that initiates a call into the agent — via `W02`'s `run_agent()` wrapper, on the app's own schedule (`W09`/`W10`) or through its manual "regenerate now" path. The agent side never independently drives production batch orchestration for the app. Concretely: `A18` (`agent-batch` CLI, `agent_user_stories.md` Phase 6), if it's ever built, is a standalone tool for someone using the agent outside the app — the app does not call it, wait for it, or treat it as a prerequisite. `W19`'s batch/weekend view, if built, is a UI layer over recommendations `W09`/`W11` already generated and cached — not a call-out to `A18`. This resolves the "which side owns batch recommendations" question raised in Phase 5/6 of both story docs.

### App-side (we mitigate these ourselves — see stories below)

- **Only Premier League has real team-history data.** `SELECT league, COUNT(*) FROM raw_matches` returns exactly one row: `('E0', 3800, max_date=2026-05-24)`. `config.yaml`'s `leagues:` list has exactly one entry. `config/competitions.yaml` registers exactly two competitions: `E0` (`competition_specific`) and a generic `international` (`general_purpose`) — there is no La Liga, Serie A, Bundesliga, or Champions League registration at all. Our sandbox mock's "EPL vs General" tier filter was directionally right but the real boundary is narrower than it implied: it isn't "big leagues vs small," it's "Premier League vs literally everything else."
- **Calling the league-history path for a non-EPL match doesn't fail cleanly — it silently degrades.** Verified by reading `ForecastService.forecast_upcoming()` (`src/forecast/forecast_service.py:314-429`) directly: the `match_type != "international"` branch **never consults `config/competitions.yaml`** — it unconditionally calls `FeatureFactory.build_for_match(league=league, ...)` and unconditionally loads the flat `"league"` model context (trained solely on E0 data), regardless of what `league` string is passed. A Real Madrid fixture routed this way gets `prediction_basis: "team_history_and_market"` and `caveat: "Full team history and market features used."` even though every rolling/team feature is cold-start-zero-filled — the only honest signal left is `cold_start_risk: true` (completeness < 0.85), buried in diagnostics, not in the headline label. `FRAI_TECHSPEC.md` §27.2 describes the competitions registry as resolving tier for "named competitions" — that wiring exists for training-time tier resolution (`model_manager.py`, `main.py`) but **not** for this live spot-inference path. Doc/code mismatch, not a misunderstanding on our part.
- **The agent's own tool selection can't be trusted to catch this either.** `config/prompts/agent_v1.txt` line 17: *"CALL forecast_league (domestic) or forecast_international (international/unknown)"* — a coarse LLM judgment call, not a registry lookup. La Liga is domestic, so the LLM has every reason to call `forecast_league` for a Real Madrid match, hitting the exact silent-degradation path above.
- **Mitigation (W03 below):** the app must decide `match_info["league"]` itself before calling `run_agent()` — pass `"E0"` only for actual Premier League fixtures (confirmed via a hardcoded allowlist for now, since the registry isn't consulted at the layer that would need it), and omit `league` entirely for everything else. `agent_prd.md`'s own CLI docs already establish this convention ("Omit `--league` for international fixtures — agent uses `forecast_international`"), so this isn't a new pattern, just enforcing an existing one at the app boundary since the engine won't enforce it for us.
- **Team-name mismatches between football-data.org and the ML engine.** `config/team_mapping.json` + `TeamNameMapper` (now source-agnostic per `FRAI_TECHSPEC.md` §27.3's ingestion restructuring) already handle Understat/FotMob naming variants — reusable, not a rebuild — but football-data.org's own naming conventions haven't been added to it. A mismatch here means `FeatureFactory.build_for_match` silently returns a cold-start row for a team that *does* have real history, just under a name the mapper doesn't recognize yet.
- **Recommendation generation is slow and not free — resolved via scheduling (D2a), not caching-on-first-request.** `run_agent()` is a real LLM (Ollama or Anthropic) + one Tavily search call per match, 10-30s per agent_techspec.md §7. Rendering "today's edges" for N fixtures live would mean N of these on a page load; instead, generation happens on two schedules (end-of-day batch, per-match T-30 refresh) using the concurrent, fault-tolerant pattern already proven in `_run_backtest_concurrent()` (§13), and the dashboard only ever reads from cache. This trades the "slow on page load" problem for a new one: **the backend process must stay running continuously** for the schedule to actually fire — see Operational below.
- **football-data.org has no odds on its free tier (D1a/D2b).** Verified against the pricing page directly: the Free tier is scores/fixtures/schedules/tables only; "Pre-Match Home/Draw/Away odds" is a separate €15/month add-on that itself requires a paid base plan. This is more than an odds-freshness nuance — without real odds, `run_agent()`'s workflow (agent_techspec.md §5: forecast tool called *before* web_search, using "explicit fallback odds defaults if none provided") means `value_edge`/`implied_probability` would be computed against placeholder numbers, not the LLM reliably searching out real current odds first. A second provider (The Odds API, D2b) is now required, not optional.
- **`direct_bet` with `current_odds: null` is a real, observed agent output** (agent_techspec.md §18.3 — this crashed the staking simulator before it was patched there). Our UI/API layer needs its own defensive handling, independent of that fix, since we're a new consumer of the same loosely-typed output.
- **`extract_recommendation` only validates key presence, not value types** (agent_techspec.md §8, §17) — a market could come back with `value_edge: "high"` (a string) and pass the agent's own validation. Our FastAPI layer needs its own Pydantic validation with graceful degradation (flag/hide the malformed market), not blind trust that the agent's schema guarantees hold.

### Cross-team (agent/ML-engine-side; app can work around but not fix)

- **`min_odds_threshold`/`min_value_edge` are prompt-level instructions, not code-enforced** (agent_techspec.md §17, confirmed still true) — nothing stops the LLM from emitting `direct_bet` below the 2.0 floor. **Resolved (2026-07-11):** bounds widened and made code-enforced — decimal odds must fall in `[1.2, 11.0]` (American −500 to +1000) for a `direct_bet`, not just `>= 2.0`. Tracked as `agent_user_stories.md` A29 (Phase 10), which adds a `max_odds_threshold` config field (didn't exist before — only a floor did) and enforces both bounds in code rather than prompt-only. The app should still not blindly trust the bound holds for every historical/cached recommendation generated before A29 ships.
- **Corners markets (`home_corners`/`away_corners`) cannot be auto-scored.** `_market_correct()` (agent_techspec.md §11.1) always returns `None` for them — there's no numeric line field on `MarketRecommendation`, only the free-text `selection` string (e.g. `"over_4.5"`), which isn't reliably parseable across runs. **Status: accepted for now, revisit later (2026-07-11)** — closing this properly requires a schema change to `MarketRecommendation` (a numeric line field), which isn't worth the engineering investment yet. Corners stay excluded from auto-settlement (W13) indefinitely until this is revisited, not just "for v1."
- **LLM output isn't reproducible run-to-run** (agent_techspec.md §18.6 — snapshot replay key misses from LLM-regenerated tool arguments; separately, final recommendations vary run-to-run even in live mode). This matters for us specifically because a user's logged bet should be tied to *the recommendation they actually saw*, not a fresh regeneration — confirms the bet tracker must snapshot the full `MatchRecommendation` at log time. **Partially mitigated by design (2026-07-11):** W10's T-30 refresh now only re-runs `run_agent()` when the odds have actually changed since the last generation (see W10/W11 below) — minimizing unnecessary re-invocations reduces how often this non-reproducibility is even exercised, though it doesn't make a single re-run deterministic.
- **Result-leakage defenses are a mitigation, not a guarantee** (agent_techspec.md §18.7 — one pilot match leaked a real result into a "historical" agent run despite two layers of defense). **Status: accepted for now, revisit later (2026-07-11)** — low relevance for live recommendations on genuinely upcoming fixtures today, but worth a closer look before this app grows a "review past agent calls" feature using `SnapshotStore`, or before the agent-side snapshot corpus scales up for other reasons.

### Operational

- **The forecast engine needs a local Ollama daemon (or an Anthropic API key) to answer anything.** **Confirmed decision (2026-07-11): local LLM (Ollama) for now**, revisit only if that changes later. Default `config/agent_config.yaml` is `provider: ollama`, `model: llama3.1:8b` — running the FastAPI backend requires Ollama installed and running on the same machine. Not currently called out anywhere as an app setup prerequisite — worth adding to a setup doc when one exists.
- **`raw_matches` was last refreshed 2026-05-24.** **Re-checked (2026-07-11) — this is not neglect, it's the football calendar.** `data/raw/football_data/E0_2526.csv` was actually re-scraped as recently as 2026-07-05 (file mtime), but the max match date in `raw_matches` is still 2026-05-24 because that's genuinely the end of the 2025/26 Premier League season — there's nothing newer to fetch until pre-season/2026/27 fixtures start being played (~August). The underlying concern still stands once the new season starts: nothing runs `python main.py refresh-data` on a schedule today. **Resolved as a story:** `documents/user_stories.md` Phase 17, US#109 — weekly scheduled refresh of all scraped data.
- **The backend must run continuously for D2a's scheduled jobs to fire at all.** Closing the laptop or stopping `uvicorn` means the end-of-day batch and any pending T-30 refreshes silently don't happen. A single-user local prototype doesn't need 24/7 uptime guarantees, but the scheduler should detect missed windows on startup (e.g. no batch ran for today) and catch up rather than silently staying empty until the next scheduled fire. **Sequencing decision (2026-07-11):** the scheduler (W08/W09/W10) is deliberately built *last*, right before going live — see the note at the top of Story Dependencies below.
- **The Odds API's free tier is genuinely tight.** ~500 credits/month, and a live-odds call costs `markets × regions` credits. Scoped to 1 market × 1 region for E0-only fixtures (D2b), this comfortably covers a season's worth of EOD + T-30 calls today, but there's no slack for adding markets, regions, or leagues later without hitting a paid tier. **Resolved (2026-07-11):** a usage counter is now explicit in W07's acceptance criteria (not just "tracks usage" vaguely). Separately, **exploring a better-fitting odds API is now tracked as a future story (W24)** rather than assumed settled — The Odds API was chosen as the free, zero-friction starting point, not necessarily the long-term answer.

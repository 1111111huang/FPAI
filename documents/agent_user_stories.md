## PHASE 10: Output Validation Hardening

> Motivated by the web app integration (`documents/app_user_stories.md`) becoming a second, independent consumer of `MatchRecommendation` output. `extract_recommendation` (`src/agent/schema.py`, agent_techspec.md §8) only validates that the 7 top-level keys are present and that `overall` is one of its 4 valid literals — nothing else is checked. A market's `recommendation_type` isn't validated against its 3 valid values; `confidence` isn't validated against `low`/`medium`/`high`; and none of the numeric fields (`current_odds`, `min_odds`, `ml_probability`, `implied_probability`, `value_edge`) are type-checked at all — a model could return `value_edge: "high"` and extraction would succeed. The failure just moves downstream to whatever code first assumes the type: `staking.py`'s `float(...)` calls today, and now potentially the app's backend/frontend too. BUG-013 (`documents/bugs.md`) is a related special case of this same gap: `current_odds: null` is valid JSON and passes today's checks, but is semantically wrong when paired with `recommendation_type: "direct_bet"`. A29 extends the same validation layer with a second, wider semantic rule: an explicit min/max odds band for `direct_bet`, code-enforced instead of prompt-only.
